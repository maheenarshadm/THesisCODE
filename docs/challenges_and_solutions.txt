CHALLENGES ENCOUNTERED IN SEARCH-BASED TEST DATA GENERATION FOR
DMN-GOVERNED RELATIONAL DATABASES, AND HOW THEY WERE ADDRESSED
================================================================

Context
-------
This document summarizes the real, measured engineering challenges
encountered while building a DynaMOSA-based (Dynamic Many-Objective
Sorting Algorithm) search pipeline that generates synthetic relational
test data satisfying both (a) a set of business rules expressed as DMN
(Decision Model and Notation) decision tables, chained together into a
Decision Requirements Diagram (DRD), and (b) the relational schema's own
integrity constraints (NOT NULL, PRIMARY KEY / UNIQUE, FOREIGN KEY). Each
compiled DMN rule (one row of one decision table, fully grounded against
its own upstream dependencies) is treated as one search objective; the
whole rule set for a case study is optimized simultaneously via a shared
population, with coverage measured against a real, executable case
study (FLEX2 -- a university academic-regulations system with 151
compiled, grounded rule instances after fixes described below).

Every challenge below was found through direct investigation of real
data (compiled rule sets, archived search state, generated SQL validated
against a live SQLite database) rather than assumed from first
principles, and every fix was measured before and after with concrete
numbers -- both because that discipline caught several of the bugs
below, and because it is the standard this document tries to model for
a methodology section: a claimed improvement is only a "finding" once
someone has actually re-run the pipeline and looked at the number.


CHALLENGE 1: Representing multi-level rule dependencies as search
objectives (the "DRD chain problem")
--------------------------------------------------------------------
Problem. A DMN decision table's own rule can reference the OUTPUT of an
upstream decision as one of its own input facts (e.g., a course-load
rule that reads "the student's current academic warning status," itself
the output of a separate Academic Warning Status decision). Treating
each rule as an independent search objective in isolation, without any
notion of this dependency graph, has two failure modes: (a) a downstream
rule's own condition can never be evaluated meaningfully until a
concrete upstream branch has actually been selected and grounded into a
real value, and (b) crediting a downstream objective as "covered" before
its upstream dependency is itself satisfied produces a logically
inconsistent dataset (a row asserting eligibility that depends on a
warning-status fact no generated data actually establishes).

Solution. Every compiled rule instance carries its own
`grounded_upstream_branches` -- the exact list of upstream
"decision::rule" branches its condition transitively depends on,
populated at compile time by walking the DRD's own information-
requirement edges. An objective only becomes ACTIVE for the search
(exerts any selection pressure at all) once every branch it depends on
has already been covered by the archive. This is the "Dyna" part of
DynaMOSA: the active objective set grows monotonically as the run
progresses and earlier layers of the dependency graph are solved,
rather than every objective competing for search attention from
generation zero regardless of whether it is even meaningfully
evaluable yet.

Example. `Course Load Limit::Rule_1::via::Academic Warning Status::
Rule_1` only activates once `Academic Warning Status::Rule_1` itself
reaches fitness 0.0 in the archive; a directly-verified invariant in the
pipeline's own regression suite asserts that no chained objective is
ever credited as covered while its own declared dependency is not.


CHALLENGE 2: Independent grounding of the same upstream decision
produces mathematically unsatisfiable rules
--------------------------------------------------------------------
Problem. A single compiled rule can require the same upstream decision
twice, through two different paths (e.g. once directly, in its own
suppression logic, and once nested inside a different chained
dependency needed to ground a separate variable). The original grounding
logic chose a concrete upstream rule for each occurrence completely
independently. This could -- and did -- select two different rules of
the same real-world decision for what should have been one single,
consistent fact, producing a compiled condition that required the same
variable (e.g. `priorWarningCount`) to equal two different literal
values simultaneously under one logical AND. No search algorithm can
ever satisfy such a rule; it is unsatisfiable by construction, not
merely difficult.

Diagnosis. Traced one permanently-stuck rule's full compiled condition
by hand after an escape-hatch mutation mechanism (Challenge 6) failed to
move it. Found the contradiction directly, then wrote a general,
mechanical detector that walks every compiled rule's condition tree,
collects every `variable = literal` equality constraint, and flags any
variable forced to two different values. This measured the true blast
radius rather than treating the one found instance as isolated: 192 of
FLEX2's 391 compiled records (49%) shared this exact defect.

Solution. Replaced the independent-grounding logic with a
commitment-respecting backtracking search: a single, shared dictionary
mapping `decision name -> chosen rule id` is threaded through every
grounding need of one record, including nested ones. Once a decision is
committed to a rule anywhere while grounding a record, every other
reference to that same decision -- however deeply nested -- must reuse
the identical rule; the search still backtracks correctly when a
different top-level choice legitimately needs its own independent pick.

Result (measured). FLEX2's compiled record count dropped from 391 to
151 -- confirmed directly that 0 of the resulting 151 have any residual
self-contradictory equality constraint (down from 192/391), with zero
regression in unrelated case studies (OpenMRS, Spree, jBilling compiled
counts unchanged) and zero new record-id collisions. Search coverage on
the corrected corpus reached the same absolute count as before (80
covered objectives) but against the true, much smaller denominator, and
12x faster (84.5s vs. previously wasting effort trying to solve rules
that could never be solved by any algorithm).


CHALLENGE 3: Shared-row interference across simultaneously-evolving
objectives
--------------------------------------------------------------------
Problem. DynaMOSA evolves ONE shared population where a single candidate
(row-set) is meant to satisfy many objectives at once. The first working
version gave every objective the SAME physical "first row" of a table as
its own working context. Two different objectives needing different
column values on the very same physical row overwrote each other every
time either one was mutated.

Diagnosis. Categorized every uncovered branch by its actual failure
state rather than guessing. Found that 58 of 83 uncovered branches
(~70%) failed with an outright "missing column" error -- not a scoring
weakness, not genuine difficulty, but objectives stepping on each
other's data.

Solution ("focal-per-objective"). Every objective is given its OWN
dedicated row per table it actually needs a row for, created lazily the
first time that objective is picked for mutation and reused from then
on. An individual in the population is therefore a pair (shared
candidate, per-objective row map), not a bare row-set; crossover was
extended so that when a table's row-set is swapped between two
individuals, every objective's own dedicated row for that table travels
with it consistently.

Result (measured, same search budget before/after). Archive coverage:
20/103 -> 50/103 (roughly 2.5x). Final-dataset (simultaneous) coverage:
6/103 -> 15/103 (also roughly 2.5x). Runtime cost grew ~3.5x, a real and
disclosed cost of every objective now maintaining its own state instead
of sharing one row.


CHALLENGE 4: The same failure mode, one level deeper -- aggregate and
existence checks sharing an entire table
--------------------------------------------------------------------
Problem. Challenge 3's fix covered leaves that read a single row through
a per-objective context (a specific column comparison, a category
lookup). It deliberately did NOT cover leaves that need to COUNT or
check EXISTENCE over a whole table (e.g. "how many lectures has this
student attended," "does a passing prerequisite registration exist") --
these scanned the entire shared table with no notion of which objective
a given row belonged to. Once many objectives mutate the same shared
population, one objective's aggregate count could be silently inflated
or corrupted by another, entirely unrelated objective's own rows landing
in the same table.

Diagnosis. This was only found by actually producing and inspecting a
real, materialized SQL file end to end (not just trusting the search's
own internal archive numbers) -- a discipline worth stating explicitly:
"the search says 81/151 objectives are solvable" and "the delivered
dataset actually satisfies 81/151 objectives at once" are different
claims, and only checking the second one exposed this bug. The
delivered dataset in fact satisfied only 20/151 simultaneously, a number
suspiciously IDENTICAL across two different random seeds -- itself a
clue that something structural, not merely difficult, was going on:
with no per-objective isolation, an existence check reads TRUE the
instant ANY objective's row has ever landed in the shared table, which
happens for nearly every commonly-touched table well before the run
ends, regardless of seed.

Solution. Introduced row-ownership tagging: a reserved bookkeeping key
on each row records which objective created it. Aggregate/existence/
join-count evaluation logic now only scans rows tagged for the current
objective plus untagged rows (genuinely shared reference data, such as
foreign-key parent rows synthesized by repair logic). This is inert by
default (a single-objective caller that never tags anything sees zero
behavior change) and is stripped back out before real SQL/CSV is
emitted, since it is search-time bookkeeping, not schema data.

Result (measured). This fix was necessary and correct -- it removed a
real, confirmed defect -- but on its own it did NOT raise the
final-dataset coverage number; if anything it dropped slightly (from the
old, artifact-inflated 20/151 to an honestly seed-sensitive 17-19/151).
Diagnosing this honestly (rather than declaring victory or reverting the
fix) led directly to Challenge 5 below, which is where the real gain
came from.


CHALLENGE 5: Final-dataset coverage capped far below archive coverage
for a structural reason, not a bug
--------------------------------------------------------------------
Problem. After Challenge 4's fix, archive coverage (how many objectives
were EVER solved by SOME individual across the whole run) sat at
81/151, but final-dataset coverage (how many are solved SIMULTANEOUSLY
by the ONE candidate actually materialized) sat at only 17-19/151. The
strategy up to this point picked one individual out of the FINAL
generation's own population -- the one that happened to satisfy the most
objectives at once. But a Many-Objective Sorting Algorithm is explicitly
designed to spread its population across a front of SPECIALISTS, each
covering a handful of objectives well, never to converge the whole
population onto one GENERALIST individual that covers everything at
once. Picking one population member was always going to leave most of
the archive's own hard-won progress unused, for a reason that has
nothing to do with row-sharing bugs.

Solution ("merge-the-archive"). Build the final candidate directly from
the archive instead: for every objective the archive ever covered, pull
that objective's own best-ever rows (its dedicated context row, plus
every row tagged for it) out of its own best-ever individual, and merge
all of them into one shared candidate. A single schema-repair pass runs
once on the fully assembled whole, since a table now holding rows merged
from many independently-evolved individuals was never checked as a
combined whole before -- repair only ever ADDS a missing required value,
never overwrites one a search-tuned row already carries.

A methodological point worth stating for a paper: the merged result was
never trusted just because the rows were "already proven correct" in
isolation. It is always re-evaluated for real against the actual merged,
repaired candidate, and any objective that regresses in the merge is
reported explicitly rather than silently accepted. This caught two real
bugs before they could produce a false success:
  (a) An unrelated, pre-existing bug in the evaluation harness itself:
      it rebuilt a fresh, un-offset set of scenario values for
      re-evaluation instead of reusing the ones the actual search run
      had used (every objective's own placeholder values are shifted by
      a large per-objective offset during seeding, to keep independent
      objectives' rows from numerically colliding). This silently broke
      re-evaluation of scenario-dependent facts in every benchmark ever
      run with the old harness, independent of the merge logic itself.
  (b) A real bug in the merge logic: one rule legitimately owns TWO
      different rows in the same table in its own archived individual --
      its own dedicated context row, and a separate row it merely
      "owns" for counting purposes (e.g. the specific course registration
      that satisfies a prerequisite check). The first version of the
      merge conflated the two, letting the second overwrite the first
      whenever both landed in the same table -- confirmed directly on
      one regressed rule, where a count that should have read 1 came
      back as 0. Fixed by keeping "this objective's own true context
      row" and "every other row this objective merely owns" as two
      strictly separate operations during the merge.

Result (measured, after both bugs above were fixed). Final-dataset
coverage: 17-21/151 -> 81/151, VERIFIED with zero regressions, at both
of two different random seeds tried -- exactly matching archive
coverage, i.e. every objective the search could ever solve at all is now
present, simultaneously, in the one dataset actually delivered. A ~4x
improvement, not an incremental one.


CHALLENGE 6: Distinguishing "hard" from "impossible" -- provable
infeasibility inside the DMN model itself
--------------------------------------------------------------------
Problem. After the fixes above, a residual set of objectives remained
permanently unreached regardless of search budget. Simply running more
generations is indistinguishable, from the outside, between "this needs
more time" and "this can never be solved by construction." Treating the
former as the latter wastes effort forever; treating the latter as the
former produces false confidence that "we just need a better search."

Diagnosis. Ran a single-objective local search with a generous iteration
budget against one representative stuck rule with NO population
competition at all, to isolate whether the population dynamics were the
bottleneck. It converged quickly, then hard-stopped at a nonzero
distance-to-target with zero further improving moves available for the
rest of the budget. Tracing that specific rule's own compiled condition
by hand found the actual cause: its own condition required a fact to
equal a specific value, but that same fact had already been fixed, by
the rule's own upstream grounding, to a DIFFERENT literal value earlier
in the same compiled record. Since a grounded literal is not something
the search is allowed to change, this made the rule provably
unsatisfiable by its own construction -- not merely difficult.

Solution. Built a general, three-valued (true / false / unknown)
constant-folding evaluator: it walks a rule's condition tree and
short-circuits AND / OR / NOT exactly like ordinary boolean logic
wherever every variable involved is already a fixed, grounded constant,
leaving anything that still touches a genuine free variable as unknown.
Applied to both a rule's own condition and to every earlier rule it must
suppress (for first-applicable-rule hit-policy semantics), this proves
infeasibility at compile time, mechanically, for the whole corpus at
once, rather than one hand-traced example at a time.

Result (measured). 53 of FLEX2's 151 compiled rules (35.1%) are provably
infeasible this way, confirmed to have zero overlap with the set of
rules the search actually covers. Combined with a separate, already-
identified compile-time gap (rules whose upstream fact could not be
structurally classified at compile time, 17 rules), this exhaustively
and exactly accounts for the entire 151-rule corpus: 81 covered + 53
provably infeasible + 17 compile-gap-blocked = 151. Framed positively:
excluding the rules that are infeasible or blocked for reasons outside
the search's control, 81 of 81 genuinely searchable-and-resolvable
objectives are covered -- 100%. This reframes "why isn't coverage
100%" from an open question into an exact, defensible characterization
of the corpus's own real boundary conditions, which is itself a finding
about the source DMN model, not a shortcoming of the search.


CHALLENGE 7: A silent bug in domain-value enumeration made one rule
class unsolvable despite having a trivially satisfiable leaf
--------------------------------------------------------------------
Problem. One rule needing a single, simple comparison to become true
found literally zero improving moves across a 500-iteration local-search
budget, despite the comparison being trivially satisfiable in principle.

Diagnosis. Traced the value-selection logic directly. An earlier rule
in the same hit-policy table (which the current rule must ensure does
NOT also fire, for first-applicable-rule semantics) has its own
equality condition on the same variable. The value-enumeration logic
walked that earlier rule's condition with the SAME polarity as the
current rule's own condition -- treating the earlier rule's required
value as something worth TRYING, when it is in fact the one value that
must be AVOIDED (the earlier rule's condition needing to be false is
exactly what makes the later rule reachable at all). The search kept
re-offering the one value that could never work, forever.

Solution. Corrected the polarity: an earlier rule's own condition is now
walked as a negated context, while the current rule's own condition
keeps its original (non-negated) polarity. A general fix, not targeted
at the one discovered rule.

Result (measured). The specific rule that exposed this now converges in
a single search step (down from finding zero improving moves in 500).
Full regression suite unaffected; population-level search coverage rose
by one full objective at scale, confirming the fix helps beyond the one
hand-traced example.


CHALLENGE 8: Attention dilution as the true objective count grew
--------------------------------------------------------------------
Problem. Fixing the grounding and duplication bugs above (Challenge 2)
correctly enlarged the honestly-counted objective set roughly fourfold
(from a previously-hidden ~83 effectively-visible objectives to several
hundred genuinely distinct ones, before the infeasibility work in
Challenge 6 further corrected the denominator down to 151). The
population loop's original variation step mutated exactly one randomly
chosen active objective per offspring, per generation, regardless of how
large the active objective set had grown -- so as the true problem size
increased, each individual objective received a proportionally shrinking
share of the search's total attention every generation. Simply scaling
up population size and generation count did not help and in one
controlled comparison made results measurably WORSE for the same
compute budget, confirming this was a structural bottleneck rather than
a resource-shortage one.

Solution. Each offspring individual now attempts mutation against
several distinct, randomly sampled active objectives per generation, the
count auto-scaling with the size of the currently active objective set
(so a small run behaves identically to before, and only a large active
set gets proportionally more attempts). A second, complementary fix
gives each of those picks a "burst" of several sequential attempts,
sized by how many independent leaf variables that specific rule's own
condition actually has -- a rule needing five independent facts to align
at once genuinely needs proportionally more within-record optimization
depth than a rule needing only one, purely as a function of its own
structure, never hardcoded to any specific named rule.

Result (measured, same population/generation budget throughout). Single
random pick per generation: 43/391 objectives. Adding multi-objective
picking: 48/391. Adding the per-record mutation burst on top: 80/391 --
nearly double the multi-pick-only result, and the run's own coverage
history showed healthy, steady growth up to a new, higher plateau,
rather than the flat line that scaling population/generation size alone
had produced.


CHALLENGE 9: A search that only optimizes for provability produces
data that is technically correct but not domain-realistic
--------------------------------------------------------------------
Problem. Once all of the above was fixed and delivering the full,
verified 81/151 objectives simultaneously, manual inspection of the
actual generated SQL surfaced a different kind of gap: a rule computing
"attendance percentage" as attended-lectures divided by lectures-held
was satisfied using only 3 lectures held per course offering -- the
CHEAPEST value that could still cross the rule's own 80% threshold, not
a value chosen for real-world plausibility. This is not a defect in the
search (it was never asked to optimize for realism, only for rule and
schema correctness), but it is a real, previously invisible gap: some
facts have a known, domain-true value that a generated dataset should
respect even though no rule anywhere mathematically requires it.

Solution. Built a small, general, configuration-driven mechanism rather
than hand-coding the one discovered case: a JSON file maps
{case_study: {variable_name: fixed_value}}, keyed by the same
free-variable name every part of the search already uses internally.
Wherever a value is pinned this way, the value-selection logic jumps
straight to the pinned value instead of searching for the cheapest one
that merely proves the rule; the initial data-seeding logic seeds that
many rows directly from the start; and the search's own random-jump
diversification mechanism (used elsewhere to escape local optima, see
below) is explicitly forbidden from perturbing a pinned variable away
from its correct value. One configuration entry applies uniformly to
every rule in the corpus that happens to use that same variable name --
no per-rule special-casing anywhere in the pipeline's logic.

Result (measured). Pinning "lectures held per course offering" to a
realistic 30 (instead of the search's own previous minimal-proof value
of 3): the generated dataset's course offerings now correctly show 30
held lectures each, with attendance rows recomputed relative to that
realistic denominator (one student at 25/30 ≈ 83.3%, correctly above
the 80% eligibility threshold; another at 3/30 = 10%, correctly below
it). Overall objective coverage was unaffected (still 81/151, verified,
zero regressions) -- confirming the mechanism changes WHICH values the
search lands on without changing WHETHER a rule is provable.


CHALLENGE 10: Confirming a purely greedy, single-leaf search cannot
always escape a genuine local optimum -- and honestly reporting when a
proposed fix does not work
--------------------------------------------------------------------
Problem. Even after the fixes in Challenges 3, 7, and 8, a subset of
objectives plateaued at a stable, nonzero fitness value with no further
improvement even after extending the run from 40 to 70 generations at
the same population size -- a flat coverage line for 45 generations
straight, which disproved the hypothesis that the plateau was merely a
"needs more time" problem.

Diagnosis. Isolated one representative stuck rule with a single-
objective local search (no population, no competition), which
hard-stopped after only 3 accepted moves despite a 300-iteration budget.
This is coordinate descent's own well-known failure mode: a search that
only ever changes one variable at a time, accepting a move only when it
is immediately and strictly improving, can never discover a solution
that requires SEVERAL variables to move together, if no single one of
those moves is independently improving on its own.

Solution attempted. Added a probabilistic "kick" mechanism: with a
modest fixed probability, a chosen variable's value is replaced by an
unconditional, non-greedy random jump instead of the usual greedy
best-value search -- a standard, safe diversification move in
population-based search generally (the archive discipline guarantees a
temporarily-worsened individual can never overwrite a better answer
already found).

Result (measured, honestly, as a negative finding). At the same search
budget, coverage with the kick mechanism landed at the exact same count
as without it. Extending the run length again (the same 70-generation
test that had proven the plateau was real) confirmed the identical
count once more. The mechanism was not harmful, but it did not break
this specific plateau either -- reported plainly as a negative result
rather than adjusted or reframed to look like a success, and it directly
motivated tracing the underlying cause by hand instead of continuing to
tune search parameters speculatively, which is what led to discovering
the actual grounding-consistency defect described in Challenge 2.

Methodological note for the paper
----------------------------------
Two practices recur across nearly every challenge above and are worth
stating explicitly as part of the methodology: (1) every claimed
improvement was measured against a real, executable artifact -- a
generated SQL file validated against a live database engine with
referential-integrity enforcement turned on, never a hand-computed or
assumed number -- and (2) every fix was cross-checked for regressions
against the full existing test/self-check suite and, where the fix
touched the search's own internal state, against an independent
before/after diff of exactly which objectives changed status, not just
the aggregate count. This is what surfaced several of the compounding
bugs above (Challenges 4/5 in particular) that a purely aggregate-metric
view would have missed or misattributed.
